# pr-review - 確認を挟む PR レビュー

PR を読み解いて要約と論点を提示し、**最終判断はユーザーに委ねてから** GitHub に反映する。
勝手に Approve / Request changes をしないことがこのスキルの主目的。

## 入力

PR の URL または PR 番号。無ければ「レビュー対象の PR URL を教えてください」と聞く。

## 手順

### 1. 情報収集

```bash
gh pr view <PR番号> --repo <owner/repo> --json title,body,author,state,baseRefName,headRefName,additions,deletions,changedFiles,url
gh pr diff <PR番号> --repo <owner/repo>
```

diff が大きい場合はスクラッチパッドに保存し、`grep -n '^diff --git'` でファイル単位に分けて読む。
整形のみの差分（インデント変更、配列展開など）はノイズとして切り分け、実変更だけを追う。

### 2. リポジトリ側の裏取り

diff だけで判断せず、必ずローカルリポジトリで周辺コードを確認する。

```bash
ghq list -p <リポジトリ名>
git fetch origin <headRefName>
git show origin/<headRefName>:<path>   # 変更後の全体像を読む
```

最低限、以下は diff の外側まで確認する。

- 変更されたリソースを**参照している側**（呼び出し元、module の呼び出し、IAM ポリシー、変数の受け渡し）
- 失敗時・異常系に通るパス（エラーハンドリング、後片付け、リトライ）
- 「変更なし」と書かれている箇所が本当に変更されていないか

### 3. 変更点の要約を提示

ユーザーにまず**リスト形式**で要約を出す。

- ファイル単位に、何がどう変わったかを1行ずつ
- **構成（アーキテクチャ・処理フロー）が変わる場合は、その旨を明示する**
  - 例: 「直列1タスク → PreSetup後に2並列 + fail-fast」
- 削除された機能・失われた経路があれば必ず書く
- 整形のみの差分は「実変更なし」と切り分けて書く

### 4. 気になった点をユーザーに確認する

**この時点ではまだ GitHub に何も投稿しない。**

気になった点を番号付きで挙げ、それぞれについて次を書く。

- 何が問題になりそうか
- なぜそう考えたか（コードの根拠。ファイルパスや状態名を示す）
- この PR で新たに生じるものか、既存の挙動か
- 軽微なものは「（軽微）」と明記して重要度を分ける

最後に「問題の有無を教えていただければ、コメントを残すかApproveします」と確認する。

### 5. ユーザーの回答に従って反映

ユーザーが「問題ない」と判断した項目は**コメントに含めない**。
残った項目だけを対象にする。

コメントを残す場合:

```bash
gh pr review <PR番号> --repo <owner/repo> --comment --body-file <file>
```

Approve する場合:

```bash
gh pr review <PR番号> --repo <owner/repo> --approve --body-file <file>
```

投稿後は `gh pr view <PR番号> --repo <owner/repo> --json reviews` で反映を確認する。

## コメントの書き方

- 日本語、Markdown、絵文字なし
- 断定せず「〜という理解で合っていますか」と確認の形にする
- 根拠（ファイル・状態名・行）を示す
- 良い変更は良いと書いたうえで懸念を述べる
- 指摘して終わりにせず、**対応案を複数提示する**（実装での対応 / 別PRでの対応 / 運用手順での対応 など）
- 「既に想定済み・別PR対応なら問題ありません」と逃げ道を残す

## やってはいけないこと

- ユーザーの確認なしに Approve / Request changes する
- diff だけを見て周辺コードを確認せずに指摘する
- ユーザーが「問題ない」と言った項目をコメントに残す
- 重要度の異なる指摘を並列に並べる
